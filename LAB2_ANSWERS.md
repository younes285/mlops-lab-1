Question 1

Look at pyproject.toml and uv.lock. What changed?

pyproject.toml was updated to include the new dependencies required for training and experiment tracking, such as MLflow, PyTorch, torchvision, and scikit-learn.

uv.lock is used to lock the exact resolved versions of the project's dependencies so that the same environment can be reproduced on another machine. In my case, pyproject.toml changed after installing the libraries, while uv.lock did not show an additional modification in the final Git status.

Question 2

What are --backend-store-uri and --default-artifact-root used for? What is the difference between metadata and artifacts?

--backend-store-uri sqlite:///mlflow.db tells MLflow where to store metadata, such as experiments, runs, parameters, metrics, timestamps, and run information.

--default-artifact-root ./mlruns specifies where MLflow stores artifacts, such as trained models and other output files.

So:

mlflow.db → experiment/run metadata
mlruns/   → files and model artifacts

Metadata describes the experiment, while artifacts are the actual files produced by the run.

Question 3

Why shouldn't mlflow.db and mlruns/ be tracked by Git or DVC?

They are local outputs generated by MLflow every time experiments are run. They are not source code, so tracking them with Git would unnecessarily add frequently changing and potentially large files to the repository.

They also should not be tracked by DVC because DVC is being used for versioned project data such as the Food-11 dataset, while MLflow already manages experiment metadata and artifacts. Tracking the same MLflow outputs with DVC would duplicate responsibilities and create unnecessary storage/versioning overhead.

MLflow automatically creates a new experiment with that name.

Question 5

Difference between mlflow.log_param and mlflow.log_metric? Why does metric have step?

mlflow.log_param records a configuration value that is normally fixed for the entire run, such as:

lr = 0.001
batch_size = 32
epochs = 5

mlflow.log_metric records a measured result produced during training, such as:

train_loss
val_loss
val_accuracy

Metrics can change during training, so step indicates when the value was recorded, such as the epoch number:

Epoch 1 → val_accuracy = ...
Epoch 2 → val_accuracy = ...
Epoch 3 → val_accuracy = ...

This allows MLflow to display metric curves over time. Parameters do not need step because they remain fixed for the run.

Question 6

Where are the params, metric charts and model artifact? Where does the model live on disk?

In the MLflow run page, the Parameters section contains values such as learning rate, batch size, epochs, dataset, and model. The Metrics section contains train_loss, val_loss, val_accuracy, and test_accuracy, and MLflow can display their evolution across epochs.

The trained ResNet18 model is available as a logged model/artifact in MLflow.

Because the tracking server was started with:

--default-artifact-root ./mlruns

the artifact storage is rooted under the local project's mlruns/ directory. MLflow organizes the actual files inside its experiment/run/model artifact structure.

Question 7

Which learning rate gave the best val_accuracy? Is higher always better?

For batch size 32, our results were:

Learning rate	Final validation accuracy
0.01	11.13%
0.001	52.19%
0.0001	70.62%

So among the tested learning rates, 0.0001 produced the highest final validation accuracy.

No, a higher learning rate is not always better. In our experiments, 0.01 performed much worse than the smaller learning rates. A learning rate that is too large can cause optimization to make updates that are too aggressive and fail to converge well.

Question 8

What pattern is visible in the parallel coordinates plot?

The parallel coordinates plot showed that, with batch size 32, reducing the learning rate improved validation accuracy substantially:

lr 0.01    → 11.13%
lr 0.001   → 52.19%
lr 0.0001  → 70.62%

For learning rate 0.001, increasing the batch size from 32 to 64 slightly improved the final validation accuracy:

batch 32 → 52.19%
batch 64 → 55.38%

Therefore, in these particular runs, the learning rate had a much larger effect on validation accuracy than the tested batch-size change.
